# Taste
- Prefers pragmatic, temporary workarounds (e.g., a feature-flagged dev login) to unblock development when an external dependency is unavailable, deferring the full integration until it is ready. Confidence: 0.7
- Tends to ask for a suggestion/plan, an explanation/diagnosis of an error, or a status/overview of current capabilities before implementation proceeds rather than requesting immediate action. Confidence: 0.85
- Prefers the assistant to draft ready-to-send written messages for others — teammate/agent handoffs, PR descriptions, commit messages, or suggestion messages to accompany a change — rather than just explaining an idea conversationally. Confidence: 0.8
- Wants temporary workarounds and changes-that-need-reverting tracked in a dedicated doc (e.g., `doc/temporary-changes.md`) so they can be cleaned up before launch. Confidence: 0.9
- Prefers a written progress/status document that summarizes what has been built so far and how a user can access it (startup commands, endpoints, socket events, dev-login flow), distinct from setup docs and specs. Confidence: 0.85
- Wants the assistant to proactively test already-implemented features and hunt for bugs (including deep root-cause tracing) before moving on to new work. Confidence: 0.7
- Likes checkpoint reviews after a body of work that produce a prioritized list of remaining items (bugs/risks, unfinished features, hardening and testing gaps) rather than jumping straight into the next implementation. Confidence: 0.8
- Wants features made production-ready, not just functionally working — values robustness, graceful degradation, accurate error messaging, and defensive hardening (presence TTL/heartbeats, Redis-less boot, rate limits) before declaring a phase done. Confidence: 0.8
- On the frontend, prefers to avoid repeated API calls by centralizing data access — using React Context for identity/session state and TanStack Query's cache for profile/server data rather than fetching per-component. Confidence: 0.75
- Wants the assistant to have read-only access to the frontend (full codebase) — and to not modify it — even when frontend edits aren't being requested, so it has full-stack context rather than a backend-only workspace. Confidence: 0.85
- Prefers comprehensive error logging throughout the backend — every error should produce a log line, silent catches (empty `catch {}`, `.catch(() => null)`, health checks returning `false`) should be replaced with real error/stack logging, and a global exception filter should surface errors that NestJS's default handler would otherwise swallow. Confidence: 0.85
