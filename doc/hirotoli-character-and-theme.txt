HIROTOLI — PRODUCTION-READY CHARACTER + HOME WORLD THEME IMPLEMENTATION SPECIFICATION

Document status

Production implementation specification

Basis

This document is based on the latest Hirotoli frontend and backend ZIPs
supplied for this implementation, including the existing character,
Home, world-theme, realtime, voice, Prisma and API foundations.

The document deliberately separates: 1. What already exists in the
current codebase. 2. What must be replaced or completed. 3. What must be
added for production. 4. What is future-ready but must NOT be
implemented in launch scope.

IMPORTANT: Do not start by rewriting the existing Home or Character
architecture. The current repository already contains useful production
boundaries. The implementation should preserve those boundaries and
replace the incomplete visual/asset layer underneath them.

====================================================================== 1.
PRODUCT GOAL
======================================================================

The launch goal is intentionally small:

Open Home -> See a beautiful Hirotoli 3D village -> See your own 3D
character -> See other Home members when they are present -> Chat with
Home members -> Talk using Home voice

Launch does NOT include: - character walking - running - jumping - free
camera exploration - Home construction - furniture placement - room
decoration editor - large character marketplace - battle pass - gacha -
event currency at launch - multiple independent Home worlds - a full
avatar creator - a large animation library loaded into Home

The implementation must nevertheless be architected so those
capabilities can be added later without rewriting CharacterRenderer or
HomeWorld.

======================================================================
2. CORE PRODUCT MODEL
======================================================================

Hirotoli has three different visual/domain concepts that MUST NOT be
mixed.

A. Global application UI theme

This is the existing application preference system.

It controls: - light mode - dark mode - system mode - UI accent

Existing frontend location: - src/lib/theme.ts -
src/components/theme/* - src/components/providers/theme-provider.tsx

This system controls the application UI.

It does NOT control the identity of the 3D Home world.

B. Permanent Home World Theme

This is the actual 3D environment displayed inside Home.

Example: - Hirotoli Village

It controls: - sky/background - ground - environment geometry -
lighting - fog - particles - decorative props - ambient audio -
character stage - camera framing

C. Future Event Theme Layer

This is a temporary server-authoritative visual layer.

Example: Hirotoli Village + The First Night event layer

The event layer may change: - sky - lighting - atmosphere - particles -
decorations - audio - event props

When the event ends, the event layer disappears and the permanent
Hirotoli Village returns.

The global light/dark UI preference must remain independent from both.

6. CHARACTER DATA CONTRACT
======================================================================

Frontend/domain shape:

type CharacterDefinition = { id: string; name: string; assetId: string;
rigId: string; defaultLoadoutId: string; unlock: { type: “free” |
“event_coins”; amount?: number; }; };

type CharacterLoadout = { characterId: string; skinId?: string; hairId?:
string; outfitTopId?: string; outfitBottomId?: string; fullOutfitId?:
string; headwearId?: string; eyewearId?: string; facewearId?: string;
footwearId?: string; accessoryIds: string[]; };

Equipment item:

type CharacterItem = { id: string; category: | “hair” | “outfit_top” |
“outfit_bottom” | “full_outfit” | “headwear” | “eyewear” | “facewear” |
“footwear” | “accessory”; assetId: string; rigId: string; attachment: |
{ type: “skinned” } | { type: “bone”; boneName: string } | { type:
“socket”; socketName: string }; compatibleCharacterIds: string[];
source: { type: “base” | “event” | “system”; eventId?: string; }; };

The renderer must receive already-validated character data.

The renderer must never decide: - whether a user owns an item - whether
an item was earned - whether an item is allowed - whether an event is
active - whether Event Coins were spent

======================================================================
7. SERVER-SIDE CHARACTER SECURITY
======================================================================

The backend is authoritative.

When PUT /characters/me or equivalent character update API is called:

1.  Authenticate user.
2.  Load requested character definition.
3.  Confirm character exists.
4.  Confirm user owns/unlocks the character.
5.  Validate every item.
6.  Confirm item exists.
7.  Confirm user owns the item if ownership is required.
8.  Confirm item is compatible with character.
9.  Confirm item category is valid.
10. Confirm mutually exclusive slots are not conflicting.
11. Confirm full outfit is not combined with incompatible top/bottom
    pieces.
12. Confirm attachment metadata is valid.
13. Save the validated loadout.
14. Return canonical server state.

The frontend must never be trusted for ownership or compatibility.

13. ASSET LICENSE GOVERNANCE
======================================================================

Every third-party asset committed to the repository must have a record
containing:

if applicable asset version where used whether modified whether
redistributed notes

Example:

assets/licenses/quaternius-character-assets.txt
assets/licenses/quaternius-village-assets.txt

Release gate: No third-party asset is production-approved merely because
it is free to download.

The license must be verified at the time the asset is actually
committed/shipped.

Do not mix assets with incompatible licenses into one supposedly
unrestricted commercial pack.

18. DEFAULT HIROTOLI WORLD
======================================================================

The launch world should be:

id: hirotoli-village

name: Hirotoli Village

version: 1

Visual composition:

Background - soft sky - distant hills - warm daytime atmosphere

Ground - stylized terrain - village paths - grass - small garden areas

Architecture - 3–5 visually distinct small structures - wooden houses -
roofs with controlled color variation - no repetitive copy/paste look

Social focal area - central plaza - fountain or small stream - bridge or
pathway - benches/meeting areas

Nature - trees - bushes - flowers - rocks - controlled vegetation
density

Lighting - warm soft key light - ambient fill - subtle contact shading -
no excessive bloom

Atmosphere - subtle fog - optional low-cost particles - no heavy
volumetric effects

Character stage - clear focal area - sufficient empty space - no props
intersecting the character - camera framing stable across supported
character models

======================================================================
19. HOME WORLD THEME VS UI THEME
======================================================================

NEVER implement:

UI dark mode -> dark Home world

or:

UI light mode -> light Home world

Instead:

UI theme: light/dark/system -> CSS/UI components

Home world: hirotoli-village -> 3D renderer

This is a hard architectural rule.

======================================================================
20. FUTURE EVENT THEME LAYER
======================================================================

The current backend already contains HomeWorldThemeLayer.

Use the following conceptual model:

Permanent Theme + 0..N active event layers -> Resolved HomeWorldTheme

Event layer:

type HomeThemeLayer = { id: string; priority: number;

environment?: Partial<HomeWorldTheme[“environment”]>; lighting?:
Partial<HomeWorldTheme[“lighting”]>; atmosphere?:
Partial<HomeWorldTheme[“atmosphere”]>; decorations?: AssetRef[]; audio?:
HomeWorldTheme[“audio”]; };

The backend must determine: - active - start time - end time - priority

The frontend consumes the resolved theme.

The frontend must NOT decide whether an event is active based on its own
clock alone.

21. HOME CHARACTER RENDERING
======================================================================

At launch:

Owner: - own character

Participant: - participant character

Maximum visible characters: 4

The character is static for launch.

Allowed launch presentation: - idle animation - subtle breathing/idle

Not allowed at launch: - movement controls - WASD - joystick -

======================================================================
22. CHARACTER IDENTITY CARD
======================================================================

Clicking/tapping a character should open an identity/action card.

Actions:

Self: - You - View Profile

Owner: - Home Owner badge

Other member: - View Profile - Add Connection - Connected - Request
Sent - Accept Request

The action must be determined from authoritative relationship state.

Do not infer connection status from Home membership.

======================================================================
23. HOME CHAT INTEGRATION
======================================================================

Home Chat is a Home-membership feature.

Rule:

If user is an active member of Home: can read Home Chat can send Home
Chat

If user is not a member: cannot read Home Chat cannot send Home Chat

Do NOT authorize Home Chat based on: - connection relationship - profile
visibility - public feed access

Desktop: - persistent right-side Home Chat panel

Mobile: - drawer/bottom sheet

Chat remains independent of the 3D renderer.

======================================================================
24. VOICE INTEGRATION
======================================================================

Voice is provided through LiveKit.

Frontend already has: - home voice context - LiveKit provider -
reconnect handling - voice hooks

Backend already has: - Home voice service - LiveKit provider

Architecture:

Browser -> Home backend authorization -> LiveKit token -> LiveKit room
-> WebRTC audio

Socket.IO is NOT the audio transport.

The backend must verify Home membership before issuing a voice token.

The Home voice room should correspond to the Home domain identity
internally.

======================================================================
25. HOME MEMBERSHIP RULES
======================================================================

Hard invariants:

1.  One active Home membership per user.
2.  Maximum 4 active Home members.
3.  One owner.
4.  Owner and participants are persistent membership records.
5.  Presence is separate from membership.
6.  Voice connection is separate from presence.
7.  Offline member remains a member.
8.  Temporary owner disconnect does not destroy Home.
9.  Capacity is rechecked atomically at accept/join time.
10. Server is authoritative.

26. IMPLEMENTATION PHASES
======================================================================

PHASE 0 — BASELINE AND FREEZE

Goal: Create a safe starting point before changing assets or visuals.

Tasks: 1. Create implementation branch. 2. Preserve current working Home
behavior. 3. Run frontend: npm run typecheck npm run lint npm run test
npm run build

4.  Run backend: npm run typecheck npm run lint npm test npm run build

5.  Run existing Home E2E/concurrency tests.

6.  Record baseline performance.

7.  Record current GLB sizes.

8.  Record current Home loading time.

9.  Record current frame rate on desktop and mobile test hardware.

10. Freeze current API contracts.

Deliverables: - clean baseline - baseline test report - baseline
performance report

Exit criteria: All existing tests/builds pass before visual migration
begins.

PHASE 1 — ASSET GOVERNANCE AND ART-DIRECTION APPROVAL

Goal: Choose the exact assets before integrating them.

Tasks: 1. Download candidate Quaternius Base Characters. 2. Download
candidate Modular Character Outfits. 3. Download candidate village
assets. 4. Download candidate props. 5. Download candidate nature
assets. 6. Download required animation samples only. 7. Create asset
manifest. 8. Create license records. 9. Compare character proportions.
10. Compare character head/hair style. 11. Compare outfit quality. 12.
Compare village style. 13. Test visual consistency between character and
village. 14. Approve final art direction.

Deliverables: - approved character 01 - approved character 02 - approved
initial outfits - approved village asset subset - asset manifest -
license manifest

Exit criteria: No asset enters production code before art and license
approval.

PHASE 2 — CHARACTER ASSET MIGRATION

Goal: Replace the current visual models without breaking the existing
character architecture.

Tasks: 1. Add final GLB files. 2. Add stable asset manifest. 3. Keep
character IDs: character-01 character-02

4.  Replace asset paths behind character-catalog.ts.
5.  Verify rig IDs.
6.  Verify model scale.
7.  Verify origin/pivot.
8.  Verify skeleton hierarchy.
9.  Verify mesh names or metadata.
10. Update material mapping.
11. Remove dependency on hardcoded gender-based identity logic where
    unnecessary.
12. Keep legacy resolver fallback temporarily if required for existing
    users.
13. Add migration compatibility for old character config.

Deliverables: - two final launch characters - compatible character
renderer - backward-compatible user character state

Exit criteria: Existing users do not lose character selection.

PHASE 3 — CHARACTER EQUIPMENT SYSTEM

Goal: Make clothing/accessories data-driven.

Tasks: 1. Implement item manifest. 2. Implement equipment categories. 3.
Implement attachment strategy. 4. Implement socket/bone mapping. 5.
Implement compatibility matrix. 6. Implement material cloning. 7.
Implement loadout resolver. 8. Implement server validation. 9. Implement
ownership validation. 10. Implement full-outfit exclusivity. 11.
Implement missing-item fallback. 12. Add unit tests.

Deliverables: - data-driven loadout - validated equipment system -
stable renderer API

Exit criteria: Adding a new cosmetic does not require modifying Home
components.

PHASE 4 — CHARACTER ANIMATION CONTROLLER

Goal: Introduce controlled animations without loading a huge animation
library.

Launch animations: - idle - wave - happy - sad - celebrate -
interaction-ready

Tasks: 1. Add animation manifest. 2. Load animations lazily. 3. Map
logical animation names to asset clips. 4. Implement cross-fade. 5.
Implement animation lifecycle. 6. Stop unnecessary animation when tab is
hidden. 7. Respect prefers-reduced-motion. 8. Prevent multiple animation
loops per character. 9. Add error fallback to idle. 10. Test 4
simultaneous Home characters.

Deliverables: - reusable animation controller

Exit criteria: Four characters can render without unacceptable
frame-rate degradation.

PHASE 5 — HIROTOLI VILLAGE WORLD

Goal: Replace the current procedural lobby with the actual Hirotoli
world.

Tasks: 1. Create environment manifest. 2. Create village layout. 3.
Build main path. 4. Build central plaza. 5. Add houses. 6. Add greenery.
7. Add bridge/stream/fountain. 8. Add props. 9. Add lighting. 10. Add
sky. 11. Add atmosphere. 12. Add subtle ambient audio if approved. 13.
Add character stage. 14. Add camera composition. 15. Remove/retire the
old BGMI-style HomeLobbySet as the default world. 16. Keep the old
implementation only if needed for rollback until release.

Deliverables: - Hirotoli Village v1

Exit criteria: The Home visually reads as a coherent social village
rather than a technical demo/lobby.

PHASE 6 — THEME RESOLUTION

Goal: Make the world completely data-driven.

Tasks: 1. Define hirotoli-village default theme. 2. Define version. 3.
Define environment references. 4. Define lighting configuration. 5.
Define atmosphere. 6. Define decorations. 7. Define audio. 8. Define
character stage. 9. Define camera. 10. Use HomeThemeResolver. 11. Merge
active server event layers. 12. Add deterministic priority handling. 13.
Add tests for no event. 14. Add tests for one event. 15. Add tests for
overlapping priorities. 16. Add tests for expired events.

Deliverables: - server-authoritative theme resolution - deterministic
frontend rendering

Exit criteria: A future event can add a layer without rewriting
HomeWorld.

PHASE 7 — HOME CHARACTER + WORLD INTEGRATION

Goal: Connect user character state to Home.

Tasks: 1. Load current user’s canonical character. 2. Load canonical
loadout. 3. Render own character. 4. Render other Home members. 5.
Resolve missing/invalid character state to default. 6. Add character
labels. 7. Add click/tap interaction. 8. Add identity card. 9. Add Home
Owner badge. 10. Preserve Home chat. 11. Preserve Home voice. 12.
Preserve invitations. 13. Preserve join requests.

Deliverables: - complete Home experience

Exit criteria: Owner and participants see the correct characters and
social actions.

PHASE 8 — PERFORMANCE AND WEBGL HARDENING

Goal: Make the experience production-safe on realistic devices.

Tasks: 1. Compress GLBs where compatible. 2. Compress textures. 3.
Remove unused assets. 4. Lazy-load nonessential props. 5. Lazy-load
animation clips. 6. Limit draw calls. 7. Limit dynamic lights. 8. Limit
particles. 9. Avoid expensive post-processing. 10. Dispose resources
correctly. 11. Avoid duplicate GLTF loading. 12. Cache immutable assets.
13. Pause effects when tab is hidden. 14. Respect reduced motion. 15.
Implement WebGL fallback. 16. Implement loading state. 17. Implement
model-load error state. 18. Test 4-character Home.

Measure: - initial JS size - initial 3D asset transfer - GLB transfer -
texture memory - draw calls - triangles - FPS - time to first usable
Home - memory after 10 minutes - memory after leaving/re-entering Home

Exit criteria: No obvious frame drops or runaway memory during normal
Home use.

PHASE 9 — SECURITY AND PRODUCTION HARDENING

Goal: Ensure the visual system cannot bypass backend authorization.

Tasks: 1. Character ownership validated server-side. 2. Cosmetic
ownership validated server-side. 3. Home membership validated
server-side. 4. Home Chat membership validated server-side. 5. LiveKit
token membership validated server-side. 6. Event theme timing controlled
server-side. 7. Event rewards granted server-side. 8. Event Coins
validated server-side. 9. No database access from frontend. 10. No
Prisma/database access from CharacterRenderer. 11. No secrets in
frontend. 12. Validate asset IDs against allowlisted manifests. 13.
Reject malformed loadouts. 14. Audit sensitive character/economy
changes.

Exit criteria: A malicious client cannot unlock a character/cosmetic or
access another Home’s voice/chat by modifying frontend state.

PHASE 10 — TESTING

Frontend unit tests: - character catalog - character fallback - loadout
normalization - equipment compatibility - material isolation - animation
fallback - theme resolver - event layer merge - camera layout - WebGL
fallback

Backend unit tests: - character ownership - character item ownership -
loadout validation - Home membership - Home capacity - invitation
lifecycle - join-request lifecycle - Home policy - theme resolution -
event timing - LiveKit authorization

Integration tests: - select character -> persist -> reload - equip item
-> persist -> reload - enter Home -> character visible - second user
joins -> second character visible - fourth user joins -> visible - fifth
user rejected - owner leaves temporarily -> Home remains - member
reconnects -> presence restored - voice token rejected for non-member -
Home Chat rejected for non-member

E2E: - desktop Home - mobile Home - light UI + Home - dark UI + Home -
slow network - failed asset - WebGL unavailable - reduced motion -
browser tab hidden/returned

PHASE 11 — UAT AND ROLLOUT

Goal: Release safely.

Environment: Development -> UAT -> Production

Before UAT: 1. Production build. 2. Database migration review. 3. Asset
license review. 4. Asset checksum/version record. 5. Environment
variable review. 6. LiveKit environment review. 7. Error tracking
review. 8. Performance review. 9. Mobile browser review.

UAT scenarios: 1. New user opens Home. 2. User selects character. 3.
User reloads. 4. Character remains. 5. User invites another user. 6.
User accepts. 7. Both characters appear. 8. Home Chat works. 9. Voice
works. 10. User disconnects. 11. User reconnects. 12. UI light/dark
changes. 13. 3D world remains Hirotoli Village. 14. Fourth member joins.
15. Fifth member is rejected.

Rollout: - internal test users - small production cohort - monitor -
expand gradually

Rollback: Keep the old Home world asset path available behind a
controlled rollback configuration until the new world has passed
production validation.

29. PERFORMANCE TARGETS
======================================================================

These are engineering targets, not fabricated measurements of the
current repository.

Desktop target: - smooth 60 FPS on representative modern hardware -
stable rendering with 4 characters - no continuous frame-time spikes
during idle Home

Mobile target: - stable 30+ FPS on representative mid-range devices -
adaptive effects - reduced particle density - reduced lighting
complexity - no unnecessary animation when hidden

Loading: - show useful UI immediately - show explicit 3D loading state -

Memory: - no continuous growth after entering/leaving Home repeatedly -
dispose resources on Home unmount - avoid duplicate GLTF/material copies

======================================================================
31. ERROR HANDLING
======================================================================

Character asset failure: -> show default safe character or controlled
fallback

Unknown character ID: -> character-01

Unknown cosmetic: -> ignore invalid item and use valid default loadout

Invalid loadout: -> server rejects -> frontend displays controlled
validation error

Home theme unavailable: -> default Hirotoli Village

Event layer unavailable: -> ignore event layer -> default world remains
usable

WebGL unavailable: -> accessible non-WebGL Home fallback

LiveKit unavailable: -> Home remains usable -> show “Voice isn’t
available”

Important: 3D/voice must never become a dependency for the core social
application.

41. IMPORTANT IMPLEMENTATION PRINCIPLE
======================================================================

The final system must follow this rule:

THE 3D WORLD IS A PRESENTATION LAYER. THE CHARACTER SYSTEM IS A
DOMAIN-BACKED PRESENTATION LAYER. THE BACKEND IS THE AUTHORITY. THE
GLOBAL UI THEME IS SEPARATE. THE EVENT SYSTEM IS AN EXTENSION LAYER.

Therefore:

React must not own authorization. Three.js must not own business rules.
CharacterRenderer must not own inventory rules. HomeWorld must not own
event scheduling. LiveKit must not define Home membership. CSS theme
must not define Home world theme.

This separation is what keeps the implementation production-ready.
