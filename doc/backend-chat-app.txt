# Social Chat App V1 - Backend Technical Documentation

## 1. Project Summary

This is an independent personal project.

The backend powers a live social chat website with public read-only channels for guests, Facebook and Google login, live channel messaging for authenticated users, connection requests, profiles, user settings, and one-to-one private chat between accepted connections.

## 2. Scale Target

V1 must be designed for:

- 50,000 registered/logged-in users.
- 5,000 concurrent users actively chatting.
- Public guest traffic reading channel messages.
- Multiple live public channels.
- One-to-one direct messages between accepted connections.

The system should be built professionally from day one with rate limiting, moderation, observability, and horizontal scaling.

## 3. Recommended Backend Architecture

Use a modular monolith plus separate realtime and worker processes.

Recommended deployable apps:

1. API App
2. Realtime App
3. Worker App

This avoids unnecessary microservice complexity while still supporting scale.

## 4. API App Responsibilities

The API app handles normal HTTP APIs:

- Facebook and Google auth start and callback.
- Session/token refresh.
- Logout.
- Current user.
- Profile read/update.
- Channel list.
- Channel message history.
- Connection requests.
- Connections list.
- User search.
- Reports.
- Blocks.
- Admin moderation APIs.

Recommended framework:

- NestJS with TypeScript.

## 5. Realtime App Responsibilities

The realtime app handles WebSocket connections:

- Authenticated socket connection.
- Guest read-only socket connection.
- Join/leave channel rooms.
- Send public channel messages.
- Broadcast public channel messages.
- Join/leave DM rooms.
- Send DM messages.
- Presence tracking.
- Online counts.
- Reconnection handling.

Recommended:

- NestJS WebSockets.
- Socket.IO.
- Socket.IO Redis adapter for horizontal scaling.

## 6. Worker App Responsibilities

The worker app handles background tasks:

- Moderation jobs.
- Spam detection jobs.
- Notification jobs.
- Message cleanup/retention jobs.
- Profile image processing.
- Audit/event processing.
- Scheduled data cleanup.

Recommended:

- BullMQ or a similar Redis-backed queue for V1.
- Move to Kafka/NATS later only if needed.

## 7. Core Infrastructure

Required services:

- PostgreSQL for permanent data.
- Redis for realtime presence, pub/sub, rate limits, and queues.
- Object storage for profile images.
- CDN for frontend and static assets.
- Load balancer for API and realtime services.
- Monitoring and logging system.

Recommended providers:

- PostgreSQL: Neon, Supabase, AWS RDS, or managed PostgreSQL.
- Redis: Upstash, Redis Cloud, or AWS ElastiCache.
- Object storage: Cloudflare R2 or AWS S3.
- Frontend hosting: Vercel or Cloudflare Pages.
- Backend hosting: AWS ECS, Render, Railway, Fly.io, or DigitalOcean App Platform.

## 8. Why Not Too Many Microservices In V1

Do not start with separate services for every feature.

Avoid this in V1:

- Separate auth service.
- Separate profile service.
- Separate channel service.
- Separate connection service.
- Separate DM service.
- Separate moderation service.

Instead, use:

- One API app with feature modules.
- One realtime app.
- One worker app.

This keeps development faster and easier while still allowing horizontal scaling.

Later, if traffic grows, split modules into services based on real bottlenecks.

## 10. Social OAuth Authentication

V1 supports Facebook Authentication and Google Authentication.

There must be no password login, email login, OTP login, or Apple login in V1.

Required social OAuth flow:

1. Frontend sends user to backend route: `GET /auth/facebook` or `GET /auth/google`.
2. Backend redirects to the selected OAuth provider.
3. User authorizes app with the provider.
4. Provider redirects to backend callback route.
5. Backend verifies provider response.
6. Backend fetches provider profile.
7. Backend creates or finds app user.
8. Backend creates session.
9. Backend redirects user back to frontend.

Recommended provider permissions:

- `public_profile`
- `email`, if required and approved by Facebook

Do not request unnecessary OAuth permissions in V1.

## 12. First Login User Creation

When a social OAuth user logs in for the first time:

1. Check `auth_identities` by `provider` and `provider_user_id`.
2. If found, login existing user.
3. If not found, create user.
4. Create auth identity.
5. Create initial profile.
6. Mark profile as incomplete if required fields are missing.

Initial profile can use:

- Provider display name.
- Provider avatar.
- Provider email if available.

App-specific required fields must still be collected:

- Username.
- Date of birth or age confirmation.
- Region.
- Preferred language.

## 13. Authorization Rules

Guest users can:

- Fetch public channel list.
- Fetch public message history.
- Connect to read-only public channel socket.

Guest users cannot:

- Send channel messages.
- View full profiles.
- Search users.
- Send connection requests.
- Open Connections APIs.
- Send DMs.

Authenticated users can:

- Send channel messages.
- View allowed public profiles.
- Search users.
- Manage connection requests.
- Send DMs to accepted connections.
- Report/block users.
- Manage own profile.

Admin users can:

- Mute users.
- Ban users.
- Delete messages.
- Review reports.
- Manage channels.

## 14. Database Choice

Recommended primary database: PostgreSQL.

Reason:

- Strong relational structure.
- Connections and conversations need clean constraints.
- Good indexing.
- Good transaction support.
- Easier moderation/admin queries.

Redis is required for:

- Socket.IO pub/sub adapter.
- Presence.
- Online counts.
- Rate limits.
- Short-lived caches.
- Queues.

## 16. Channel System

Channels are controlled by admins/system config in V1.

Users cannot create channels in V1.

Each channel has:

- Name.
- Slug.
- Type.
- Visibility.
- Active status.
- Sort order.
- Default flag.

The backend must provide one default public active channel.

Default channel logic:

1. Find active channel where `is_default = true`.
2. If none exists, return first active public channel by sort order.
3. If no active channel exists, return empty state.

## 17. Public Channel Guest Access

Guest users can fetch:

- `GET /channels`
- `GET /channels/default`
- `GET /channels/:slug/messages`

Guest users can connect to sockets for reading public channels, but they cannot emit message-send events.

Every message-send event must verify authenticated user server-side.

## 18. Realtime Socket Design

Use Socket.IO namespaces or gateways.

Suggested namespaces:

- `/channels`
- `/dm`

Socket rooms:

- `channel:{channelId}`
- `dm:{conversationId}`
- `user:{userId}`

Guest socket:

- Allowed to join `channel:{channelId}` for public channels.
- Not allowed to send messages.
- Not allowed to join DM rooms.

Authenticated socket:

- Allowed to join public channel rooms.
- Allowed to send channel messages.
- Allowed to join DM rooms where user is a member.

## 19. Socket Authentication

Socket handshake must support:

- Authenticated users with access token or session cookie.
- Guests with no auth.

If token is present:

- Validate token.
- Attach user to socket context.
- Check user status.

If no token:

- Mark socket as guest.
- Allow read-only public channel events.

If token invalid:

- Reject socket or connect as guest depending on product decision.

Recommended:

- Invalid token should return auth error and require refresh/login.

## 20. Channel Message Flow

When authenticated user sends a channel message:

1. Validate socket session.
2. Check user status is active.
3. Validate channel exists and is active.
4. Check message body length and content.
5. Apply per-user rate limit.
6. Apply per-channel rate limit if needed.
7. Check banned words/basic moderation.
8. Save message to PostgreSQL.
9. Publish message to Redis/Socket.IO room.
10. Broadcast to `channel:{channelId}`.

Never broadcast unsaved messages as final messages. Save first, then broadcast.

## 21. Direct Message Flow

When authenticated user sends a DM:

1. Validate socket session.
2. Check user status is active.
3. Validate conversation exists.
4. Validate sender is conversation member.
5. Validate both users are accepted connections.
6. Check neither user has blocked the other.
7. Validate message body.
8. Apply rate limit.
9. Save direct message.
10. Broadcast to `dm:{conversationId}`.
11. Send notification event to recipient's `user:{userId}` room if online.

## 22. Connection Rules

Connection request rules:

- User cannot connect to self.
- User cannot duplicate pending request.
- User cannot duplicate accepted connection.
- User cannot request a user they blocked.
- User cannot request a user who blocked them.
- Banned users cannot send requests.
- Muted users may be blocked from sending requests depending on policy.

Accepted connection rules:

- DM conversation is created when request is accepted.
- If conversation already exists, reuse it.
- Removing a connection should disable future DM sending unless reconnected.

## 25. Rate Limits

Rate limits are mandatory.

Suggested limits:

- Login callback abuse protection: per IP.
- Message send: 10 messages per 10 seconds per user.
- Channel burst limit: 3 messages per 2 seconds per user.
- DM send: 20 messages per minute per user.
- Connection requests: 30 per day per user.
- User search: 60 requests per minute per user.
- Profile update: 20 per hour per user.
- Reports: 50 per day per user.

Use Redis for rate limits.

Backend must return clear error codes:

- `RATE_LIMITED`
- `AUTH_REQUIRED`
- `USER_MUTED`
- `USER_BANNED`
- `CHANNEL_DISABLED`
- `MESSAGE_TOO_LONG`
- `CONNECTION_REQUIRED`
- `BLOCKED`

## 26. Message Limits

Suggested V1 limits:

- Channel message max length: 500 characters.
- DM max length: 1000 characters.
- No attachments in V1.
- No HTML allowed.
- Strip or escape unsafe content.
- Normalize whitespace.

## 27. Moderation Requirements

Moderation is required from day one.

V1 must include:

- Report user.
- Report channel message.
- Report direct message.
- Block user.
- Admin mute user.
- Admin ban user.
- Admin delete channel message.
- Admin delete direct message.
- Banned words list.
- Basic spam detection.
- Moderation audit logs.

Muted user:

- Cannot send channel messages.
- Cannot send DMs.
- May still read channels.

Banned user:

- Cannot login/use app normally.
- Existing sessions should be invalidated or blocked at auth check.

## 28. Presence And Online Counts

Use Redis for presence.

Suggested Redis keys:

- `presence:user:{userId}` for user online state.
- `presence:channel:{channelId}` for channel members.
- `socket:user:{userId}` for active socket IDs.

Online counts should not query PostgreSQL on every request.

Presence updates:

- On socket connect.
- On channel join.
- On channel leave.
- On disconnect.
- Periodic cleanup for stale sockets.

## 29. Redis Usage

Redis is used for:

- Socket.IO adapter.
- Pub/sub across realtime instances.
- Presence.
- Online counts.
- Rate limiting.
- Queues.
- Short-lived cache.

Do not store permanent messages only in Redis.

PostgreSQL is the source of truth for users, profiles, channels, messages, connections, and reports.

## 30. Message History

For channel messages:

- Store messages permanently or according to retention policy.
- Load recent messages with cursor pagination.
- Suggested default: latest 50 messages.
- Suggested max page size: 100.

For DMs:

- Store messages permanently unless user deletion policy is added later.
- Load latest 50 messages by default.

Pagination should use cursor based on message timestamp and ID.

## 31. Security Requirements

Required:

- Validate every request body.
- Validate every socket event payload.
- Use secure cookies if using cookie sessions.
- Use CSRF protection if needed for cookie-based auth.
- Use CORS allowlist.
- Never expose Facebook access token to frontend.
- Never store raw refresh tokens.
- Never trust user ID from frontend payload.
- Check authorization server-side for every action.
- Escape/sanitize user-generated text.
- Add helmet/security headers.
- Add audit logs for admin actions.

## 32. Privacy Requirements

Do not expose:

- Facebook provider user ID.
- Facebook access token.
- Email.
- Phone.
- Date of birth.
- IP address.
- User agent.
- Internal user status except where needed.

Public profile should expose:

- User ID or username.
- Display name.
- Avatar.
- Bio.
- Age group.
- Region if user allows.
- Languages.
- Connection status relative to viewer.

## 33. Age Safety

If the app allows users under 18:

- Store DOB privately.
- Show only age group publicly.
- Backend calculates age group.
- Do not allow users to manually choose restricted age group.
- Consider blocking adult-minor direct discovery.
- Add stricter report handling for underage safety reports.

If the first launch does not want this complexity, set minimum age to 18.

This decision must be made before launch.

## 41. Out Of Scope For V1

Do not build in V1:

- Email/password login.
- OTP login.
- Apple login.
- Posts/feed.
- Stories.
- Reels.
- Likes/comments.
- Message replies.
- Message reactions.
- Group DMs.
- Voice/video calls.
- Livestreaming.
- User-created channels.
- Monetization.
- Ads.
- Payment system.
- AI-only moderation.

## 42. Final Backend Decision

Build V1 with:

- One API app.
- One realtime app.
- One worker app.
- PostgreSQL.
- Redis.
- Object storage.
- Facebook and Google auth.
- Admin moderation.
- Load testing before public launch.

This is the right level of architecture for 50,000 registered users and 5,000 concurrent chat users without making development unnecessarily complicated.
