### Status

**Implementation specification — Production**

It covers:

* Backend

# 1. Product Principle

The most important design principle is:

> **The user should never think about a "voice room".**

Internally, the backend can use concepts such as:

* Home
* HomeRoom
* HomeMembership
* VoiceSession
* Invitation
* JoinRequest

But the user experiences:

> "Let's go to their Home."

Not:

> "Let's create a voice room."

The room is an implementation concept.

The Home is the product concept.

---

# 2. User Experience

The user experience should remain extremely simple.

Example:

```text
User 1 opens Home

        🧑
      User 1
```

User 1 opens connections.

```text
User 2        +
User 3        +
User 4        Offline
User 5        Already in your Home
User 6        3 in Home       +
```

User 1 clicks `+` next to User 2.

User 2 receives:

```text
User 1 wants you to join their Home

[Accept] [Reject]
```

User 2 accepts.

Immediately:

```text
User 1       User 2
```

Both are connected.

No room creation screen.

No room ID.

No "Join Voice Room" workflow.

No additional setup.

---

# 3. Core Domain Model

The system should be built around **Home Membership**, not around a raw Socket.IO room.

The conceptual structure is:

```text
User
 │
 └── HomeMembership
        │
        └── Home
              │
              ├── Owner
              └── Participants
```

Voice is attached to the Home membership.

---

# 4. Home

A Home represents the shared Home experience.

Conceptually:

```text
Home
 ├── id
 ├── owner
 └── members
```

Maximum:

```text
4 members
```

A Home can have:

```text
1 owner
0–3 participants
```

---

# 5. Home Membership

A membership represents the user's current membership in a Home.

Conceptually:

```text
HomeMembership
 ├── homeId
 ├── userId
 ├── role
 └── joinedAt
```

Roles:

```text
OWNER
PARTICIPANT
```

The database should enforce:

> A user can have at most one active Home membership.

This is one of the most important invariants.

---

# 6. Important Invariants

The backend must enforce these rules.

## Rule 1 — One Home per user

Invalid:

```text
User 1 → Home A
User 1 → Home B
```

Valid:

```text
User 1 → Home A
```

---

## Rule 2 — Maximum four members

Invalid:

```text
User 1
User 2
User 3
User 4
User 5
```

Valid:

```text
User 1
User 2
User 3
User 4
```

---

## Rule 3 — Only owner can remove

```text
OWNER → can remove participant
PARTICIPANT → cannot remove participant
```

---

## Rule 4 — Anyone can invite

Any active Home member can invite one of their connections.

---

## Rule 5 — Anyone can accept their own incoming requests

Any active Home member can accept/reject join requests originating from their own connections.

---

## Rule 6 — Users already in another Home cannot interact through Home invitations

If:

```text
User 1 → Home A
User 2 → Home B
```

then:

```text
User 1 cannot invite User 2.
User 2 cannot invite User 1.
User 1 cannot request User 2's Home.
User 2 cannot request User 1's Home.
```

The frontend should hide the action.

The backend must also reject it.

---

## Rule 7 — Offline does not mean leaving

```text
Membership = Home A
Presence = OFFLINE
```

is valid.

Offline users remain members.

---

## Rule 8 — Explicit leave means leaving

```text
MEMBER → Leave
```

removes the membership.

The user no longer belongs to the Home.

---

## Rule 9 — Owner explicitly leaving destroys the Home

```text
OWNER → Leave
```

results in:

```text
Home destroyed
All members leave the Home
```

---

## Rule 10 — Invitation does not reserve capacity

This is extremely important.

If User 1 invites seven users:

```text
User 2
User 3
User 4
User 5
User 6
User 7
User 8
```

the Home does not reserve seven positions.

Actual membership determines capacity.

---

# 7. Invitation Model

An invitation should be a proper domain object.

Conceptually:

```text
HomeInvitation
 ├── id
 ├── homeId
 ├── inviterId
 ├── inviteeId
 ├── status
 ├── createdAt
 └── expiresAt
```

Statuses:

```text
PENDING
ACCEPTED
REJECTED
EXPIRED
CANCELLED
```

---

# 8. Invitation Lifetime

Every invitation is valid for:

```text
20 seconds
```

Lifecycle:

```text
PENDING
 ├── ACCEPT → ACCEPTED
 ├── REJECT → REJECTED
 ├── EXPIRE → EXPIRED
 └── CANCEL → CANCELLED
```

Expiration must be determined by the server.

The frontend timer is only visual.

---

# 9. Invitation Does Not Guarantee Joining

Example:

```text
Home:

User 1
User 2
User 3
User 4
```

User 5 still has an invitation.

User 5 presses:

```text
Accept
```

The server checks the Home.

```text
Current members = 4
Maximum = 4
```

Result:

```text
HOME_FULL
```

User 5 does not join.

Frontend displays:

```text
Home is Full

This Home has reached its maximum capacity.

[OK]
```

---

# 10. Invitation Can Become Valid Again

Suppose:

```text
User 1
User 2
User 3
User 4
```

Home is full.

User 5 has a valid invitation.

User 3 leaves.

Now:

```text
User 1
User 2
User 4
```

There is a free slot.

If User 5's invitation has not expired, User 5 can accept and join.

Therefore:

> Home capacity is checked at acceptance time, not invitation creation time.

---

# 11. Simultaneous Acceptance

Suppose one slot is available.

```text
User 5 → Accept
User 6 → Accept
```

at almost exactly the same time.

Only one can succeed.

The database transaction must guarantee:

```text
4 members maximum
```

Possible result:

```text
User 5 → ACCEPTED
User 6 → HOME_FULL
```

or the reverse.

Never:

```text
5 members
```

---

# 12. Join Request

Join requests are different from invitations.

Example:

```text
User 5 = Home Owner

Home:
User 5
User 2
User 3
```

User 1 is connected to User 2.

User 1 sees:

```text
User 2
3 in Home
+
```

User 1 clicks `+`.

This creates:

```text
User 1
   ↓
Join Request
   ↓
User 2
```

Not:

```text
User 1 → User 5
```

---

# 13. Join Request Model

Conceptually:

```text
HomeJoinRequest
 ├── id
 ├── homeId
 ├── requesterId
 ├── targetMemberId
 ├── status
 ├── createdAt
 └── expiresAt
```

Where:

```text
requesterId = User 1
targetMemberId = User 2
```

---

# 14. Join Request Lifecycle

```text
PENDING
 ├── ACCEPTED
 ├── REJECTED
 └── EXPIRED
```

The current product rule is:

```text
20 seconds
```

for pending requests.

---

# 15. Join Request Capacity Check

The same capacity rule applies.

The request can exist while the Home has capacity.

But when accepted:

```text
CHECK CURRENT MEMBERS
        ↓
CHECK MAX = 4
        ↓
ACCEPT ONLY IF SLOT EXISTS
```

---

# 16. Existing-Home Restriction

If:

```text
User 1 → Home A
User 2 → Home B
```

and they are connections:

```text
User 1 ↔ User 2
```

then neither can initiate a Home invitation/request to the other.

Backend response:

```text
USER_ALREADY_IN_ANOTHER_HOME
```

The frontend should normally prevent the action from appearing, but the backend remains authoritative.

---

# 17. Room Creation

A Home does not need an explicit "Create Room" button.

The first time User 1 invites someone:

```text
User 1
```

the backend ensures User 1 has an active Home.

Conceptually:

```text
User 1
   ↓
Invite User 2
   ↓
Ensure Home exists
   ↓
Create invitation
```

If User 1 already has a Home:

```text
Reuse existing Home
```

This keeps the Home concept invisible to the user.

---

# 18. Owner

The owner is:

```text
HomeMembership.role = OWNER
```

The owner never changes during the Home's lifetime.

If the owner explicitly leaves:

```text
Destroy Home
```

There is no owner-transfer feature in this version.

---

# 19. Participant

Participants:

```text
HomeMembership.role = PARTICIPANT
```

Participants can:

* invite connections
* accept their own join requests
* reject their own join requests
* self mute
* locally mute others
* leave

Participants cannot:

* remove other members
* destroy Home

---

# 20. Presence

The existing backend already has a Redis-backed presence system.

The current system tracks user sockets and uses a TTL-based online state.

We should reuse the existing presence infrastructure rather than create another independent online-status system.

However:

> Home membership must never be stored as presence.

These remain separate:

```text
Membership
Presence
Voice Connection
```

---

# 21. Presence Example

```text
User 4

Membership:
Home A

Presence:
OFFLINE

Voice:
DISCONNECTED
```

Valid.

When User 4 returns:

```text
Membership:
Home A

Presence:
ONLINE

Voice:
CONNECTING → CONNECTED
```

# 22. Voice Architecture

Voice should not be transmitted through Socket.IO.

Socket.IO is responsible for:

* Home state
* invitations
* join requests
* membership events
* presence-related UI events
* commands
* synchronization

A dedicated SFU handles audio.

Recommended architecture:

```text
                    ┌──────────────┐
                    │   Browser    │
                    │   Hirotoli   │
                    └──────┬───────┘
                           │
             ┌─────────────┴──────────────┐
             │                            │
             ▼                            ▼
       Hirotoli API                Hirotoli Realtime
             │                            │
             │                            │
             ▼                            ▼
       PostgreSQL                       Redis
             │
             │
             ▼
       Voice Provider / SFU
```

For the first production implementation, use an SFU such as **LiveKit**, behind a Hirotoli-owned abstraction.

LiveKit provides participant management, server-side participant removal, access tokens, reconnection handling, and React/JavaScript SDKs.

The important architectural rule is:

> Hirotoli owns membership. The voice provider owns the media connection.

Do not allow the voice provider to become the source of truth for Hirotoli Home membership.

---

# 23. Voice Provider Abstraction

Do not spread LiveKit-specific code throughout the application.

Create an abstraction:

```text
HomeVoiceProvider
```

Conceptually:

```text
HomeVoiceProvider
 ├── createAccessToken()
 ├── connect()
 ├── disconnect()
 ├── removeParticipant()
 └── closeHome()
```

Then:

```text
LiveKitHomeVoiceProvider
```

implements it.

If Hirotoli later changes provider:

```text
LiveKit
     ↓
Another SFU
```

the Home domain does not need to be rewritten.

# 27. Home Table

Conceptual Prisma model:

```text
Home
----
id
ownerId
createdAt
updatedAt
```

`ownerId` should identify the owner.

A user should only have one active Home.

---

# 28. HomeMembership Table

Conceptually:

```text
HomeMembership
--------------
id
homeId
userId
role
joinedAt
updatedAt
```

Constraints:

```text
UNIQUE(userId)
UNIQUE(homeId, userId)
```

The `UNIQUE(userId)` constraint guarantees one active Home membership per user.

This is stronger than relying on application code.

# 29. Invitation Table

```text

```

Indexes:

```text
inviteeId + status
homeId + status
expiresAt
```

# 30. Join Request Table

Conceptually:

```text
HomeJoinRequest
---------------
id
homeId
requesterId
targetMemberId
status
createdAt

respondedAt
```

Indexes:

```text
targetMemberId + status
homeId + status
expiresAt
```

# 31. Why We Keep Invitations Separate From Membership

Membership answers:

> Who is actually in the Home?

Invitation answers:

> Who has been invited?

Those must never be confused.

Example:

```text
Home members = 4

Pending invitations = 20
```

is technically possible.

The Home is still only 4 members.

---

# 32. API Architecture

Use REST for business commands.

Use Socket.IO for realtime delivery.

This fits the current architecture.

Existing backend already separates API and realtime applications.

---

# 34. GET /home

Returns the current user's Home state.

If the user has no shared Home:

```text
{
  home: null
}
```

If the user belongs to a Home:

```text
{
  home: {
    id,
    ownerId,
    memberCount,
    members: [...]
  }
}
```

---

# 35. Home Member Response

Each member should contain the information needed to render their character.

Conceptually:

```text
{
  userId,
  publicUserId,
  displayName,
  role,
  presence,
  characterConfig,
  joinedAt
}
```

The frontend should not need to request each member's profile separately.

One Home response should be sufficient to render the Home.

---

# 36. Character Privacy

The current backend deliberately excludes `characterConfig` from the general profile card used across social surfaces.

That is good.

Do not add `characterConfig` globally to:

* Thoughts
* DMs
* chat messages
* generic profile cards

Instead:

> Home-specific responses explicitly include the character configuration required by the Home renderer.

This keeps the 3D character a Home-specific identity layer.

---

# 37. Connection List API

The existing connections endpoint currently returns profile information but does not include character configuration in its general public connection card.

Do not pollute the existing connection API with Home-specific fields.

Instead, create:

```text
GET /home/connections
```

This endpoint should return connection states specifically relevant to Home.

Example:

```text
[
  {
    userId,
    displayName,
    characterConfig,
    presence: "online",
    homeState: "AVAILABLE"
  },
  {
    userId,
    displayName,
    characterConfig,
    presence: "offline",
    homeState: "AVAILABLE"
  },
  {
    userId,
    displayName,
    characterConfig,
    presence: "online",
    homeState: "MY_HOME"
  },
  {
    userId,
    displayName,
    characterConfig,
    presence: "online",
    homeState: "OTHER_HOME",
    homeMemberCount: 3
  }
]
```

# 39. Invitation API

```text
POST /home/invitations
```

Request:

```text
{
  inviteeId
}
```

Server validates:

1. authenticated
2. inviter is active
3. inviter belongs to Home
4. inviter can invite
5. invitee is a connection
6. invitee is active
7. invitee is online
8. invitee is not already in a Home
9. inviter and invitee are not in different Homes
10. Home itself is valid
11. invitation isn't already pending

Then creates invitation.

---

# 40. Accept Invitation

```text
POST /home/invitations/:id/accept
```

Must execute a transaction.

Conceptual flow:

```text
Load invitation
       ↓
Validate pending
       ↓
Validate not expired
       ↓
Validate Home exists
       ↓
Validate inviter still owns Home
       ↓
Validate user has no Home
       ↓
Count members
       ↓
If >= 4 → HOME_FULL
       ↓
Create membership
       ↓
Mark invitation accepted
       ↓
Publish realtime events
       ↓
Return Home
```

---

# 41. Concurrency Protection

The acceptance transaction must prevent:

```text
4 → 5 members
```

The database transaction should lock/recheck the relevant Home state before inserting membership.

A second concurrent acceptance must fail safely.

This is one of the most important backend requirements.

---

# 42. Join Request API

```text
POST /home/join-requests
```

Request:

```text
{
  targetMemberId
}
```

Server resolves:

```text
targetMemberId
       ↓
target's current Home
       ↓
Home
```

Then validates:

* requester is authenticated
* requester is connected to target
* requester is not already in a Home
* target is in a Home
* requester is not already in target Home
* target is online
* target is an active member
* Home isn't full
* no duplicate pending request

---

# 43. Why Request Targets a Member

We must preserve the product rule:

```text
User 1
   ↓
request
   ↓
User 2
```

not:

```text
User 1
   ↓
request
   ↓
Home owner
```

The recipient of the request is the connection through whom the requester discovered the Home.

---

# 44. Leave

```text
POST /home/leave
```

If participant:

```text
Remove membership
Notify Home
Disconnect voice
```

If owner:

```text
Destroy Home
Remove all memberships
Invalidate pending invitations
Invalidate pending join requests
Close voice session
Notify all members
```

---

# 45. Remove Participant

```text
DELETE /home/members/:userId
```

Only owner can perform this.

Server verifies:

```text requester.role === OWNER
```

Then:

```text Remove membership
Remove voice participant
Invalidate their Home access
Notify them
Notify remaining members
```

```text
/home
```

Socket namespace.

Events should be domain-oriented.

### Invitation

```text

home:invitation:rejected
```

### Join requests

```text

```

### Membership

```text

```

### Home synchronization

```text
home:state
```

---

# 48. Do Not Trust Realtime Events

Socket events are notifications.

They are not authoritative commands.

For example:

```text
home:member:joined
```

means:

> "The server says a member joined."

It does not mean:

> "The frontend should independently add a member without validating the resulting state."

For important transitions, the client should be able to recover the complete Home state.

---

# 49. Home State Synchronization

The most important realtime event should be:

```text
home:state
```

It provides the authoritative current state.

If the frontend misses events because of:

* network interruption
* browser sleep
* socket reconnect
* server restart

the frontend can call:

```text
GET /home
```

and recover.

---

# 50. Realtime Architecture

The existing backend already has:

```text
API
Realtime
Redis
Fanout
Socket.IO
```

and uses Redis to bridge events between API and realtime processes.

Home should use the same pattern.

```text
API mutation
     ↓
HomeService
     ↓
Database transaction
     ↓
Fanout event
     ↓
Redis
     ↓
Realtime service
     ↓
Socket.IO
     ↓
Users
```

---

# 51. Redis

Redis should be used for:

* cross-process fanout
* realtime coordination
* short-lived Home state caches where useful
* rate limiting
* presence support

Redis should not become the permanent source of truth for Home membership.

PostgreSQL remains authoritative.

---

Suggested names:

```text

home:voice:{homeId}
home:sync:{homeId}
home:invite:rate:{userId}
home:request:rate:{userId}
```

Only introduce keys when actually needed.

Do not duplicate database state unnecessarily.

# 53. Voice Token

The browser must never receive the voice provider secret.

Backend:

```text
POST /home/voice/token
```

Backend validates:

```text user belongs to Home
Home active
```

Then generates a short-lived provider token.

Frontend receives:

```text
{
  token,
  serverUrl,
  expiresAt
}
```

---

# 54. Voice Room Identity

The internal voice room name should not expose sensitive database information.

Use a generated opaque identifier.

Example:

```text
home_voice_9d1...
```

The user never sees this.

---

# 55. Voice Membership

The database says:

```text
User 1 ∈ Home A
User 2 ∈ Home A
```

The voice provider says:

```text
User 1 connected
User 2 connected
```

These are separate.

It is possible to have:

```text
Home membership = YES
Voice connection = NO
```

This is expected during:

* offline state
* reconnect
* network failure
* browser suspension

---

# 56. Reconnection

The voice layer should handle temporary network loss without destroying Home membership.

LiveKit's current SDK supports reconnecting and emits `Reconnecting`/`Reconnected` states.

The application should therefore treat:

```text
voice disconnected temporarily
```

as:

```text
voice connection problem
```

not:

```text
leave Home
```

---

# 57. Owner Reconnection

If owner temporarily disconnects:

```text
Home remains alive
```

Owner reconnects:

```text
Home membership still exists
       ↓
Voice token generated
       ↓
Voice reconnect
```

Only explicit owner leave destroys the Home.

---

# 58. Browser Close

For implementation, browser termination should initially be treated as a **temporary connectivity loss**, not an explicit Home leave.

The server should not destroy membership simply because a socket disappears.

Explicit leave is always an application action.

This is necessary to support your rule:

> Offline does not mean leave.

---

# 59. Voice Removal

When owner removes User 3:

```text
Database:
membership removed

Realtime:
member removed

Voice provider:
User 3 forcibly disconnected
```

The removed user cannot automatically reconnect to that Home because they no longer have Home membership.

---

# 60. Self Mute

Self mute belongs to the voice layer.

The user disables their own microphone.

It affects:

```text
Other users
```

---

# 61. Local Mute

Local mute is entirely local.

Example:

```text
User 1 mutes User 3
```

Only User 1 stops hearing User 3.

No database persistence is initially required.

It can later become a user preference if desired.

---

# 65. Current Character Problem #1 — Index Keys

Current rendering uses:

```text
key={i}
```

This is not appropriate for dynamic Home membership.

When users join/leave:

```text
User 1
User 2
User 3
User 4
```

then User 2 leaves.

Index-based keys can cause incorrect component identity reuse.

Replace with:

```text
key={member.userId}
```

# 66. Current Character Problem #2 — Character Identity Is Missing

Current CharacterAvatar accepts only:

```text

```

The new system needs:


Conceptually:

```text
HomeMember
 ├── userId
 ├── displayName
 ├── role
 ├── presence
 ├── characterConfig
 ├── voiceState
 └── muted
```

Then:

```text
HomeCharacter
```

renders the character and its identity.

# 72. Character Material Isolation

This is an important refactor.

The current renderer clones the GLTF scene but changes material colors on the cloned scene.

The production renderer must ensure that each character instance owns its material state.

Otherwise:

```text
User 1 outfitColor = blue
User 2 outfitColor = red
```

could accidentally share material objects.

Use proper object/material cloning or `SkeletonUtils.clone` where appropriate.

The character instance must be visually independent.

---

# 73. Material Mapping

The current implementation identifies materials partly using mesh-name strings such as:

```text
skin
body
face
hair
cloth
shirt
outfit
```

This is fragile.

The actual GLB assets contain named materials such as:

```text
Wolf3D_Skin
Wolf3D_Hair
Wolf3D_Outfit_Top
Wolf3D_Outfit_Bottom
```

and similar model-specific materials.

Production implementation should map by known material names first.

Example concept:

```text
Wolf3D_Skin → skinColor
Wolf3D_Hair → hairColor
Wolf3D_Outfit_Top → outfitColor
Wolf3D_Outfit_Bottom → outfitColor
```

with a safe fallback.


# 90. Idempotency

Home actions must be safe against duplicate requests.

Example:

User double-clicks Accept.

Backend should not create:

```text

```

Database constraints prevent that.

The same principle applies to:

* invite
* join request
* leave
* remove
* accept
* reject

# 91. Rate Limiting

Home actions should be rate-limited.

Examples:

```text
invite
join request
accept
reject
```

Especially:

```text
User 1 → sends 1000 invitations
```

This must not be allowed.

Use the existing realtime/API rate-limit infrastructure as the foundation rather than introducing an unrelated limiter.

# 138. What We Should NOT Do

Do not build:

```text
one giant HomeService
```

Do not put business logic inside Socket.IO handlers.

Do not let the frontend decide capacity.

Do not use Socket.IO to transport microphone audio.

Do not make Redis the source of truth.

Do not create one Canvas per character.

Do not create one API request per Home member.

Do not use array indexes as character keys.

Do not expose room IDs to users.

Do not expose LiveKit/provider concepts to users.

Do not destroy membership when a socket disconnects.

Do not treat offline as leave.

Do not reserve Home slots for pending invitations.

Do not put Home-specific character data into every social profile response.

# 140. Final Character Decision

## Keep the current character system.

```text

 ↓
```

The current `CharacterScene` even already accepts multiple character configs.

But we should refactor it before using it for the production Home feature.

The target is:

```text

Production

HomeCharacterScene
 ├── HomeCharacter
 │    └── CharacterModel
 ├── HomeCharacter
 │    └── CharacterModel
 ├── HomeCharacter
 │    └── CharacterModel

      └── CharacterModel
```

One Canvas.

Up to four characters.

Stable user identity.

Independent materials.

Responsive layout.

Offline state.

Voice state.

Future animation support.

# 141. Final Architecture

The complete system becomes:

```text
                         HIROTOLI HOME
                              │
                ┌─────────────┴─────────────┐
                │                           │
          Home Domain                  Home UI
                │                           │
        ┌───────┼────────┐          ┌───────┼────────┐
        │       │        │          │       │        │
      Home   Members  Requests   Characters Voice  Controls
        │       │        │          │       │
        └───────┼────────┘          │       │
                │                   │       │
            PostgreSQL              │    Voice SFU
                │                   │
              Redis                 │
                │                   │
            Realtime ───────────────┘
                │
             Socket.IO
```

The most important separation is:

```text
PostgreSQL
    ↓
Who belongs to the Home?

Redis / Socket.IO
    ↓
Who needs to know about changes?

Voice SFU
    ↓
Who is currently connected to audio?

React Three Fiber
    ↓
Who should visually appear in the Home?
```

Each system has one clear responsibility.

# 143. Final Engineering Principle

The implementation should follow this rule:

> **Simple for the user, strict for the server, modular for the developer.**

The user should experience:

```text
Click +
Accept
Boom — we're together.
```

But underneath that simple interaction:

```text
Authentication
      ↓
Connection validation
      ↓
Home membership validation
      ↓
Capacity validation
      ↓
Concurrency protection
      ↓
Database transaction
      ↓
Realtime synchronization
      ↓
Voice authorization
      ↓
Voice connection
      ↓
Character synchronization
      ↓
Reconnect handling
```

That complexity belongs **inside the platform**, not inside the user's experience.

This is what makes the feature a proper Hirotoli core subsystem rather than a side feature.
