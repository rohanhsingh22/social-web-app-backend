# HiRotoli Launch 1

## Complete Implementation & Fix Plan

> **Purpose:** This document is the implementation roadmap for bringing the current HiRotoli codebase to Launch 1.
>
> It covers both:
>
> * **FIX / CHANGE** — existing functionality that must be corrected, hardened, refactored, optimized, or integrated.
> * **IMPLEMENT** — functionality that does not currently exist and must be built.
>
> The phases are intentionally ordered by dependency. The goal is to avoid building new features on top of unstable authentication, profile, realtime, database, or infrastructure code.

---

# 1. Launch 1 Scope

Launch 1 includes:

* Authentication & Account Creation
* Profiles
* 3D Character
* Toli
* Toli Avatar / Profile Picture System
* Public Chat
* Connections
* Direct Messages
* Thoughts
* Safety & Moderation
* Notifications
* Home & Navigation
* Worker Functionality
* Deployment & Infrastructure
* Production Testing

## New functionality

Only the following are genuinely new feature areas:

1. Toli
2. Thoughts
3. Profile Picture / Toli Avatar System
4. Notifications
5. Worker Functionality

Everything else already exists to some degree and should be treated as **existing functionality that requires fixes, hardening, refactoring, optimization, or integration**.

# 2. Core Product Rules

These rules are fixed and must not be changed accidentally during implementation.

## 2.1 User Identity

The OAuth provider identity and the HiRotoli profile identity are different.

OAuth provides:

* provider user ID
* provider email
* provider display name
* provider profile picture

HiRotoli owns:

* display name
* bio
* interests
* Toli
* profile-picture selection
* 3D character
* other profile information

The UI must use the HiRotoli profile data.

---

# 3. Display Name Rules

## Required

Display Name is required during onboarding.

A user cannot complete onboarding without it.

## Unique

Display Name must be unique.

Uniqueness should be case-insensitive.

Therefore:

```text
Rohan
rohan
ROHAN
```

must be treated as the same display name.

This must be enforced at the database/application level, not only through frontend validation.

## OAuth must not overwrite Display Name

Example:

```text
Google name:
Rohit Kumar

HiRotoli display name:
Rohan
```

HiRotoli must continue showing:

```text
Rohan
```

even if Google later changes the user's provider name.

OAuth login must never replace the user's chosen HiRotoli display name.

---

# 4. Profile Picture Rules

There are two profile-picture sources.

## Provider Avatar

The user can use their Google/Facebook provider profile picture.

If Provider Avatar is active:

```text
Login
  ↓
Read latest provider avatar
  ↓
Update stored provider avatar
  ↓
Show latest provider avatar
```

This synchronization should happen on every successful provider login.

This is necessary because a user can change their Google/Facebook profile picture outside HiRotoli.

## Toli Avatar

The user can instead choose an avatar belonging to their selected Toli.

If Toli Avatar is active:

```text
Login
  ↓
Provider avatar may be refreshed
  ↓
Toli avatar remains active
```

The provider avatar must not replace a selected Toli avatar.

## Active profile picture

The system must know which source is currently active.

Conceptually:

```text
profilePictureType:
    PROVIDER
    TOLI
```

Provider information and Toli-avatar information should be stored independently.

---

# 5. 3D Character Rules

The 3D character is completely separate from the profile picture.

Every user has a 3D character.

It is used for the user's Home/personal experience.

It is NOT used as:

* profile picture
* Thought author avatar
* chat avatar
* connection avatar
* DM avatar

Conceptually:

```text
USER
│
├── Profile Picture
│     ├── Provider Avatar
│     └── Toli Avatar
│
└── 3D Character
      └── characterConfig
```

The existing `characterConfig` must remain a first-class part of the profile.

# 6. Toli Product Definition

There are currently five predefined Tolies:

* Vector
* Wave
* Quantum
* Orbit
* Flux

Toli is a clan/community identity.

It is not a personality-test result.

It is not a gaming clan.

---

# 7. Toli Membership Rules

A user can have:

```text
0 or 1 Toli
```

Toli selection is optional.

During onboarding:

```text
Choose your Toli

[ Vector ]
[ Wave ]
[ Quantum ]
[ Orbit ]
[ Flux ]

[ Skip ]
```

If the user skips:

```text
toli = null
```

The user can continue using HiRotoli normally.

They simply do not receive a Toli chat room.

A user can later choose a Toli.

---

# 8. Toli Chat Rules

A user receives access to only the chat room associated with their selected Toli.

Example:

```text
User
  ↓
Vector
  ↓
Vector Chat
```

A Vector user should not receive access to:

```text
Wave Chat
Quantum Chat
Orbit Chat
Flux Chat
```

A user without a Toli does not receive a Toli chat room.

## Reuse existing chat architecture

Do NOT create:

```text
ToliMessage
ToliSocket
ToliRealtimeService
```

Instead reuse:

```text
Channel
ChannelMessage
Socket.IO
Redis adapter
existing moderation
existing rate limiting
existing pagination
```

The existing channel system already has `Channel` and `ChannelMessage` models and message indexes, making it the appropriate foundation for Toli rooms.

Toli channels should simply be identifiable as Toli-specific channels.

For example, conceptually:

```text
Channel
├── GENERAL
├── ENGLISH
├── HINDI
├── GAMING
├── STUDY
├── MUSIC
├── TOLI_VECTOR
├── TOLI_WAVE
├── TOLI_QUANTUM
├── TOLI_ORBIT
└── TOLI_FLUX
```

The exact enum/schema representation should follow the existing channel architecture.

---

# 9. Toli Avatar Rules

Each Toli gets a fixed collection of avatars.

Initial target:

```text
5 Tolies × 5 avatars = 25 avatars
```

Avatars should be:

* colorful
* stylized
* cartoonized
* non-realistic
* not near-real human portraits

Fixed assets can remain frontend/static assets for Launch 1.

No object-storage system is required for these fixed Toli avatars.

## Validation

The backend must validate:

```text
selected Toli
      +
selected avatar
```

The avatar must belong to the user's current Toli.

The frontend must not be trusted to enforce this.

---

# 10. Toli Changes

If a user changes Toli:

```text
Vector
  ↓
Wave
```

the currently selected Vector avatar cannot remain active.

The user must select a valid Wave avatar.

The old Vector avatar does not need to be deleted.

The active combination must always satisfy:

```text
profilePictureType = TOLI
AND
avatar belongs to current Toli
```

# 11. Thoughts Product Definition

Thoughts is a text-only social feed.

There are no images or videos in Thoughts for Launch 1.

A user can:

* open Thoughts
* view thoughts
* create a thought
* open/read a thought
* like
* comment
* share
* hide
* report
* open the author's profile
* connect with the author where appropriate

---

# 12. Thoughts Feed

Two main tabs:

```text
For You
Fresh
```

## Fresh

Fresh should prioritize recently created content.

## For You

For You uses deterministic/rule-based ranking.

No ML system is required for Launch 1.

The ranking can consider:

* freshness
* interests
* Toli relevance
* meaningful interactions
* quality
* conversation quality
* discovery
* author diversity
* reports
* hides
* spam
* repetition

The target is not simply:

```text
most likes = highest
```

The target is:

> What thought might make this user glad they opened HiRotoli?

---

# 13. Thoughts Candidate Pipeline

The implementation should conceptually follow:

```text
Candidate Thoughts
        ↓
Safety Filtering
        ↓
Interest Matching
        ↓
Toli Matching
        ↓
Freshness
        ↓
Quality / Conversation Signals
        ↓
Discovery
        ↓
Author Diversity
        ↓
Final Feed
```

This should be implemented as a deterministic scoring service so the ranking rules can evolve without rewriting the feed API.

---

# 14. Thoughts Cold Start

A new user has little or no interaction history.

For cold-start users:

* prioritize fresh content
* mix topics
* mix authors
* include popular/high-quality content
* use Toli when available
* use interests when available

Do not create a complex ML pipeline for Launch 1.

---

# 16. Notifications — Launch 1 Scope

Notifications are intentionally limited.

Only these notification types are implemented:

## 16.1 Connection Request

User A sends a connection request.

User B receives:

```text
New connection request
```

## 16.2 Connection Accepted

User B accepts the request.

User A receives:

```text
Connection accepted
```

## 16.3 New DM

A user receives a new direct message.

They receive a notification.

The notification system must work correctly with online and offline users, but **offline invite notifications are not part of Launch 1**.

## 16.4 Legal Notice

The platform can send legally important/system-required notices.

Examples:

* terms update
* privacy update
* legally required notice

## Explicitly excluded

Do NOT implement notifications for:

* Thought likes
* Thought comments
* Thought shares
* Toli activity
* offline user invitations
* marketing
* promotional activity
* general social activity

This scope must remain intentionally small for Launch 1.

# 18. Worker Functionality

The existing worker application is currently incomplete/placeholder-oriented.

Worker functionality should be implemented only for jobs that genuinely belong outside the request/realtime process.

The worker should eventually handle:

* asynchronous notification processing where useful
* notification fan-out where necessary
* cleanup jobs
* expired session cleanup
* other explicitly asynchronous workloads introduced by Launch 1

Profile image processing/upload work remains deferred.

Do not build an unnecessary background-job architecture for every operation.

---

# 19. Worker Architecture

The desired structure is:

```text
API
 │
 ├── validates request
 ├── writes required DB data
 └── publishes background job
              │
              ↓
           Redis Queue
              │
              ↓
           Worker
              │
              ├── processes job
              ├── retries failures
              └── records/logs result
```

Realtime work should remain in the realtime application.

CPU/background work should move to the worker.

Do not make the API wait for jobs that do not need to be synchronous.

# PHASE 1 — Critical Foundation Fixes

This is the first actual coding phase.

Do not implement Toli or Thoughts until the critical foundation is stable.

---

## 1. OAuth State Security

The OAuth flow needs cryptographic state protection.

Implement:

```text
OAuth start
    ↓
generate cryptographically random state
    ↓
store state in Redis with short TTL
    ↓
redirect provider
    ↓
callback
    ↓
validate state
    ↓
delete state
    ↓
continue login
```

Reject:

* missing state
* invalid state
* expired state
* reused state

---

# 2. OAuth Profile Synchronization

Separate:

```text
provider-owned fields
```

from:

```text
HiRotoli-owned fields
```

## Provider-owned

Synchronize:

* provider avatar
* provider email if appropriate
* provider metadata

## HiRotoli-owned

Never overwrite:

* displayName
* bio
* Toli
* interests
* profile-picture choice
* 3D character

---

# 3. Provider Avatar Synchronization

Every successful OAuth login should update the stored provider avatar.

Example:

```text
Google Avatar A
     ↓
first login
     ↓
DB

Google Avatar B
     ↓
later login
     ↓
DB updated to B
```

However, if:

```text
profilePictureType = TOLI
```

the UI continues using the Toli avatar.

---

# 4. Display Name Enforcement

Current profile structure has `displayName` and a username field. The final product identity must be based on the user-entered Display Name.

Current schema already contains:

```text
displayName
```

and an index on it.

The implementation must decide the final database representation and then enforce true uniqueness.

For PostgreSQL, implement case-insensitive uniqueness correctly rather than relying on normal string comparison.

The final implementation must support:

```text
Rohan
```

being unavailable if:

```text
rohan
```

already exists.

---

# 5. Refresh Token Rotation Race

Refresh token rotation must be atomic.

Problem:

```text
Request A ── refresh ──┐
                       ├── same old token
Request B ── refresh ──┘
```

Both requests must not successfully rotate the same refresh token.

Use an atomic DB update/transaction/locking strategy.

Expected behavior:

```text
old refresh token
       ↓
first request → succeeds
       ↓
old token revoked

second request using old token
       ↓
rejected
```

---

# 6. Malformed Refresh Token

Validate refresh token format before querying Prisma.

Expected format:

```text
sessionId.secret
```

Reject malformed values with an authentication error rather than allowing malformed input to reach database queries and cause a server error.

---

# 7. Access Token Validation

Review the current access-token strategy.

The project currently performs server-side session checks during access-token validation.

Because the project uses Neon/PostgreSQL, unnecessary database work on every request can add latency.

Prefer:

```text
JWT signature
+
expiration
+
issuer
+
audience
```

for normal access-token verification.

Use session state for:

* refresh
* revocation
* account state changes
* security-sensitive checks

Keep the access-token lifetime short.

Do not remove server-side session control.

---

# 8. JWT Hardening

Add explicit:

```text
issuer
audience
```

validation.

Ensure production secrets are mandatory.

Remove dead/unused JWT configuration.

If an old refresh JWT secret is no longer needed because refresh tokens are opaque, remove the dead configuration rather than maintaining two refresh-token concepts.

---

# 9. Authentication Transport Simplification

Avoid unnecessarily maintaining two access-token transports.

Preferred model:

```text
Refresh token
    ↓
HttpOnly Secure cookie

Access token
    ↓
memory
    ↓
Authorization header
```

The frontend already has in-memory access-token handling and refresh deduplication.

Keep one clear responsibility for each token.

---

# 10. OAuth Refresh Duplication

The callback success flow currently risks triggering duplicate session restoration.

Make the flow:

```text
OAuth callback
      ↓
one session restoration
      ↓
one refresh
      ↓
store access token
      ↓
application starts
```

Do not perform two independent refresh calls.

---

# 11. Socket Authentication

Socket connections must always use the current access token.

Before reconnect:

```text
ensure fresh access token
      ↓
connect/reconnect
```

Do not allow a stale access token to remain attached to reconnect attempts.

Apply this to:

* channel socket
* DM socket
* notification socket

---

# 12. Rate Limiting

Verify that the intended throttling guard is actually applied globally where required.

Do not assume configuration alone means the guard is active.

Protect:

* authentication
* refresh
* onboarding/profile operations
* connection requests
* Thought creation
* Thought interactions
* chat
* DMs
* notification endpoints

Use feature-appropriate limits.

---

# PHASE 2 — Database & Architecture Preparation

Before implementing new features, prepare the data model.

---

# 1. Toli Model

Create a Toli entity.

Conceptually:

```text
Toli
├── id
├── name
├── description
├── motto
├── createdAt
└── updatedAt
```

The five records are seeded:

```text
Vector
Wave
Quantum
Orbit
Flux
```

Do not allow normal users to create new Tolies in Launch 1.

---

# 2. Profile → Toli

Add a nullable Toli relationship:

```text
Profile
   ↓
toliId?
```

Nullable is required because Toli selection is optional.

Add an index on `toliId`.

---

# 3. Toli Avatars

Because the avatar collection is fixed, there does not need to be a database row for every static image if the avatar metadata can safely be represented as fixed keys.

A practical representation is:

```text
avatarType:
    PROVIDER
    TOLI

avatarKey:
    vector_01
    vector_02
    ...
```

The backend must validate the key against the user's current Toli.

The final DB shape should avoid storing arbitrary frontend-provided URLs as trusted avatar identity.

---

# 4. Provider Avatar Storage

Keep provider avatar information associated with the OAuth identity.

The existing `AuthIdentity` already has:

```text
providerDisplayName
providerAvatarUrl
```

and should be used for provider-owned data.

The profile should contain the active profile-picture selection rather than treating the provider identity itself as the visible profile identity.

---

# 5. Thoughts Models

Create the minimum required data model.

Conceptually:

```text
Thought
├── id
├── authorId
├── body
├── status
├── createdAt
├── updatedAt
└── deletedAt
```

Interactions:

```text
ThoughtLike
ThoughtComment
ThoughtShare
ThoughtHide
ThoughtReport
ThoughtEvent
```

Do not create unnecessary tables until the actual interaction requires them.

---

# 6. Thought Indexing

At minimum support:

```text
authorId
createdAt
status
```

For feed queries:

```text
(status, createdAt)
```

and appropriate author/interaction indexes.

Feed performance should be considered from the beginning.

---

# 7. Notifications Model

Create one notification model.

Conceptually:

```text
Notification
├── id
├── recipientId
├── type
├── title
├── body
├── metadata
├── readAt
├── createdAt
└── expiresAt
```

Add indexes for:

```text
recipientId + createdAt
recipientId + readAt
```

# PHASE 6 — Notifications Implementation

---

# 1. Notification Service

Create one central notification service.

Example:

```text
NotificationService
├── connectionRequest()
├── connectionAccepted()
├── newDm()
└── legalNotice()
```

The notification service owns notification creation.

Feature modules should not directly duplicate notification database logic.

---

# 2. Connection Request

When request succeeds:

```text
ConnectionService
      ↓
NotificationService
      ↓
create notification
```

Only create the notification after the connection request is successfully persisted.

---

# 3. Connection Accepted

Same pattern:

```text
accept connection
      ↓
persist status
      ↓
notification
```

---

# 4. New DM

When a new DM is successfully persisted:

```text
DM
 ↓
recipient notification
```

If the recipient is actively viewing the conversation, the frontend can avoid unnecessary UI noise while still maintaining notification state according to the chosen read/unread rules.

---

# 23. Rules for Implementation

These rules should be followed throughout development.

## Rule 1 — Do not rewrite working systems unnecessarily

If the existing connection, DM, moderation, or channel architecture is sound, extend it.

Do not rebuild it just because a new feature is being added.

---

## Rule 2 — Backend is the authority

Frontend validation improves UX.

It does not provide security.

The backend must validate:

* Toli
* avatar
* display name
* Thought permissions
* chat access
* notifications
* moderation
* ownership

---

## Rule 3 — Reuse infrastructure

Prefer:

```text
existing Channel
existing ChannelMessage
existing Socket.IO
existing Redis adapter
existing moderation
existing rate limiting
existing connection system
existing DM system
```

instead of creating parallel systems.

---

## Rule 4 — Keep new systems modular

Thought ranking should be separate from the Thought controller.

Notification creation should be centralized.

Worker jobs should have clear handlers.

Toli should not contain chat implementation.

Profile should not contain OAuth implementation.

---

## Rule 5 — Database constraints matter

Anything that must always be true should be enforced as close to the database as practical.

Examples:

```text
unique display name
unique OAuth identity
one profile per user
one Toli per profile
unique connection pair
unique interaction where applicable
```

## The existing schema already uses database constraints for several important relationships, such as unique provider identity and connection pairs.

## Rule 6 — Do not add future features accidentally

Launch 1 does NOT include:

* custom profile image upload
* profile-image processing workers
* Toli competitions
* Toli rankings
* Toli events
* Toli roles
* Toli invitations
* Thought media
* ML recommendation models
* Thought-like notifications
* Thought-comment notifications
* offline user invite notifications
* marketing notifications

These can be future work.

# 25. Final Principle

The goal is not:

> "Build five new features."

The goal is:

> **Turn the existing HiRotoli codebase into one coherent Launch 1 product without breaking the systems that already work.**

Therefore the implementation strategy is:

```text
STABILIZE
   ↓
PREPARE
   ↓
IMPLEMENT
   ↓
INTEGRATE
   ↓
TEST
   ↓
SECURE
   ↓
LOAD TEST
   ↓
DEPLOY
```

Every phase should finish with its own verification before the next dependent phase begins.

This prevents a situation where Toli, Thoughts, Notifications, authentication, sockets, and the worker are all changed simultaneously and failures become difficult to isolate.
